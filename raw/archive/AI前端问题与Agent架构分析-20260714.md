# AI Coding Agent 前端问题与 Agent 架构分析

分析时间：2026-07-14

---

## 一、AI Coding Agent 处理前端容易出问题的原因与应对

### 核心原因

前端代码的特殊性导致 AI Agent 在修改时容易引入问题：

- **状态分散**：前端状态分布在 store、组件 state、URL、localStorage、CSS class 之间，改一个地方容易引发连锁反应
- **视觉正确性无法通过编译验证**：后端 API 返回正确的 JSON 就算对，前端组件渲染出来是否"正确"需要人眼判断
- **样式耦合**：CSS/Tailwind 的改动影响范围不确定，AI 没有视觉反馈
- **组件嵌套和 props 流**：改父组件可能破坏子组件，改子组件可能和父组件的期望不一致

### 社区主流应对策略

1. **给 AI 更多约束文件（CLAUDE.md / 系统 prompt）**：明确告诉它前端的组件规范、样式系统、状态管理模式
2. **拆小任务**：一次只改一个组件或一个功能点，不要"重构整个页面"
3. **提供截图或描述期望 UI**：让 AI 知道目标长什么样
4. **锁定不动的文件**：明确告诉 AI 哪些文件不要动
5. **先审后写**：让 AI 先出方案，确认后再改代码

## 二、当前项目减少前端问题的具体建议

### 1. 创建 CLAUDE.md

项目缺少 CLAUDE.md。建议写一份包含：

```
前端技术栈：Next.js 14 + React 18 + TypeScript + Tailwind CSS + Zustand
组件目录约定：pages 在 src/app/，组件在 src/components/，store 在 src/store/，API 在 src/services/
样式系统：DigitalHuman 组件使用 styled-jsx global，其他页面使用 Tailwind
状态管理：Zustand with persist middleware
API 层：统一通过 src/services/digitalHumanApi.ts 封装 fetch
禁止改动的文件（除非明确要求）：layout.tsx, globals.css, store 的接口类型定义
前端修改规则：
- 不要修改已有组件的 props 接口，除非确认所有调用方都同步修改
- 不要删除或重命名 CSS class，除非确认没有其他地方使用
- 新增功能优先在现有组件内部添加，不要拆分新文件除非功能完全独立
```

### 2. 当前前端结构的脆弱点

- `DigitalHumanFloat.tsx` 有 694 行 styled-jsx。AI 改样式时容易误伤其他 class 或在添加功能时把样式块弄乱
- `DigitalHumanMatterWorkspace.tsx` 有 306 行、大量内联逻辑和 20+ 个 state 变量，AI 改这个文件时容易对状态关系判断错误
- `DigitalHumanChat.tsx` 依赖 store + workspace 子组件 + router，交互链路长

### 3. 给 AI 下达前端任务时的模板

当让 AI 改前端时，明确告诉它：
- "只改 XXX 组件的 YYY 功能"
- "不要改样式 / 不要动 styled-jsx 块"
- "这个组件的状态流是 store → Chat → Workspace，不要改变数据流方向"

### 4. 前端修改后必须验证

```bash
cd frontend && npx tsc --noEmit
```

每次改完前端后必须跑这个命令验证类型安全。编译通过不代表 UI 正确，但至少能拦截接口不匹配的问题。

## 三、当前 Agent 系统架构评估

### 架构分层（合理）

- **Router 层**（`digital_human_agent.py`）：纯 HTTP → 领域映射，不含业务逻辑
- **Facade 层**（`facade.py`）：统一入口，组装依赖
- **Runtime 层**（`labor_runtime.py` + `labor_graph.py`）：状态机 + LangGraph
- **Repository 层**（`persistence.py`）：PostgreSQL 持久化
- **Tool 层**（`executor.py` + `registry.py`）：策略执行器

### 做得好的地方

- 幂等性控制（`begin_action` / `finish_action` + idempotency key）
- Advisory lock 防并发（`locks.py`）
- 明确的状态枚举，不依赖魔法字符串
- 法源验证的安全边界（无来源则阻断，不降级）
- 预算控制（时间/token/cost/tool_call 四重限制）

### 可优化的地方

1. **Repository 层会话管理**：每个方法都 `SessionLocal()` → `try/finally → close()`。如果一次 graph invoke 涉及多次 DB 操作，频繁开关连接有性能开销。考虑用 `contextvar` 或 scoped session 做请求级连接复用。

2. **`LaborDisputeGraph` 的节点太胖**：`_execute` 和 `_ensure_context` 方法各自约 40 行，混合了状态判断、工具调用、验证和持久化。如果后续加更多步骤或工具，这里会膨胀。可以把"步骤执行"和"状态转换"分开。

3. **错误恢复不够显式**：`start()` 方法里 catch `RUN_BUSY` 后静默忽略，但 graph 可能执行了一半。如果 lock 获取失败，当前只是返回最新 snapshot，用户不知道上一次执行是否中途出错。

4. **Facade 单例**：`get_legal_agent_facade()` 的全局单例在测试中不好替换，而且 `auto_sync_authorities=True` 写死了。考虑用 Flask `app.extensions` 或 `g` 对象管理生命周期。

5. **前后端接口契约**：`digitalHumanApi.ts` 里的类型定义和后端 `snapshot()` 返回的字段是手动同步的。如果后端加一个字段、改一个字段名，前端不会报错但会丢数据。建议用 OpenAPI schema 或至少在 CLAUDE.md 里写明"后端 snapshot 返回的字段列表，前端 DigitalHumanAgentRun 必须同步"。

## 总结

| 问题 | 答案 |
|------|------|
| AI 改前端出问题有解决方案吗 | 有共识但没银弹：给约束文件、拆小任务、锁定文件、先审后写 |
| 当前项目怎么减少这种情况 | 写 CLAUDE.md、前端修改后必须跑 `tsc --noEmit`、每次指定改动范围 |
| Agent 控制方式合理吗 | 架构分层合理，状态机设计扎实。优化点在 DB 会话管理、节点拆分、前后端契约同步 |

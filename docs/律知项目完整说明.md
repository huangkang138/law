# 律知智能法律服务平台｜项目完整说明

> 整理时间：2026-09-20。本说明依据当前项目源码和项目记录编写，面向未参与开发、需要完整了解项目的人。文中“已实现”表示仓库中存在相应功能链路；某个部署环境是否连通、模型与法源是否可用，仍取决于该环境的实际配置和运行状态。

## 1. 项目是什么

律知是一个将 AI 交互与法律业务功能结合的智能法律服务平台。用户可以在平台中提出法律问题、审查合同、检索法律信息、起草文书、使用法律计算工具，也可以围绕一件纠纷持续整理材料和办理进度。项目不是单纯的问答机器人：对于需要严肃处理的劳动争议，它提供从咨询、建案、材料整理、事实确认、证据检查、规则分析、法律依据核对，到人工确认文书草稿的完整流程。

项目是一个**综合法律服务平台**。用户可以独立使用咨询、合同审查、法律检索、纠纷整理、文书起草、模拟法庭、法律图谱和辅助工具。其中，青年就业劳动权益具有更深入的案件工作台和法律 Agent 流程：实习、兼职和毕业初期就业场景中的模糊叙述，可逐步转为有出处的材料、确认事实和受控处理任务。劳动案件是平台的重点能力之一，不能用它代指整个项目。

平台的定位是**辅助用户理解和准备法律事务**。它不充当执业律师，不自动认定证据效力，不承诺赔付或胜诉，也不会替用户向仲裁机构提交申请。

## 2. 整体功能

平台由一个统一入口和多项法律服务组成。下表描述功能在当前仓库中的位置与作用；功能有页面和接口，不等于所有业务都达到劳动争议主线同样的闭环程度。

| 功能领域 | 用户看到和完成的事情 | 主要位置 |
| --- | --- | --- |
| 首页与导航 | 首页展示普法问答、合同审查、法律检索、风险预警四个主入口；顶栏连接其他法律功能和独立的案件工作台。 | `/`、全站顶栏 |
| 法小助咨询 | 多轮问答、历史会话、数字人反馈、语音输入与朗读、可点击的功能入口；当问题符合条件时，提供劳动分流或转入案件办理。 | `/chat`、全站悬浮入口 |
| 案件与纠纷 | 创建与恢复案件，确认法域，整理材料，核对事实和证据，运行劳动分析，查看风险与法源，确认并导出仲裁申请草稿。 | 案件工作台 |
| 合同审查 | 上传合同，查看审查摘要、风险项和历史记录；审查过程支持流式结果。 | `/contract` |
| 法律内容与文书 | 法律检索、案情分析、相似文书/案例、文书起草、法律意见等页面与相应服务。 | `/case-analysis`、`/similar-documents`、`/document-drafting` 等 |
| 模拟法庭与知识图谱 | 模拟庭审交互，以及法律节点和关系的可视化浏览、管理。 | `/debate`、`/knowledge-graph` 等 |
| 辅助工具 | 劳动补偿、诉讼费、仲裁费、执行费、时效等计算和查询入口。结果应结合输入口径与实际规则人工复核。 | `/legal-calculator` 及各工具页面 |

这些功能共享平台入口，但业务处理方式不同。普通问答偏向解释和引导；合同审查处理合同文本；劳动案件工作台是目前最强调事实、证据、法源、执行记录和人工确认的深度流程。

### 2.1 普法问答和数字人

`/chat` 是法小助的主要对话页。用户可进行多轮问答、新建或切换会话、阅读历史消息、复制回答、使用语音输入和朗读，并通过回答中的真实按钮进入其他业务功能。Rive 数字人根据对话、加载和语音状态呈现不同表情与动作；全站还有悬浮咨询入口。消息和会话由后端保存，流式事件用于逐步展示回答。法小助帮助用户理解问题和找到功能入口，并不因收到一句话就自动完成正式办案。

### 2.2 合同审查

`/contract` 面向已有合同的用户。用户上传合同文件，或使用页面内置示例，查看审查摘要、具体风险条款、风险原因和修改建议，并可查看此前的审查记录。前端接入合同上传、详情、历史和流式审查接口。审查结果是对合同文本的辅助检查，使用者需要结合完整合同、交易背景和实际签署意图判断，不能把单条风险提示当成最终法律结论。

### 2.3 法律检索与案情参考

顶栏“法律检索”聚合**法律案情推断、相似法律文书、相似案件解释、法律意见咨询**四个子入口。案情推断帮助拆解已知事实与争议；相似文书和案件解释提供写法或情形上的参考；法律意见咨询帮助整理问题与意见。用户可以只使用其中一个功能，并不需要先创建工作台案件。这一栏目中的参考内容须核对事实相似性和来源；它不应被描述成全站所有回答都经过劳动 Agent 的官方法源验证。

### 2.4 案件与纠纷

顶栏“案件与纠纷”包含**纠纷整理、纠纷中心、案件工作台**三个不同入口。纠纷整理面向一段杂乱叙述，提炼当事人、事件经过、争议焦点、证据线索和缺失信息。纠纷中心进一步提供取证、维权路径、文书、预测和提醒等分项功能。案件工作台则围绕具体案件持续保存材料、事实、分析、法源和草稿，目前以劳动争议的深度办理链路为重点。三者不是同一个页面的三个名称，也不能假定用户在纠纷整理中的文字已经自动变成工作台的确认事实。

### 2.5 文件起草

“文件起草”包含文书起草、合同起草，并有法律意见起草相关页面。用户描述文件类型、用途、参与方和关键要求，后端生成相应草案，项目提供起草记录的查询、更新和删除等接口。这是面向多类文件的通用起草能力；工作台中须经审批的劳动仲裁申请草稿则有独立的案件、事实、法源和审批约束。两者都需要用户核对当事人、金额、日期和未确认事项。

### 2.6 模拟法庭

`/debate` 提供围绕案情的模拟庭审交互，用户可观察原告、被告、法官等角色如何陈述、反驳和追问。项目包含文字和语音相关体验；后端为庭审会话提供 WebSocket 双向通信。这个模块用于练习表达与发现争议焦点，并不连接真实法院，也不产生有法律效力的庭审结论。

### 2.7 法律图谱

法律图谱相关页面以节点和关系组织法律概念、条款、案例等信息，支持搜索、浏览及二维/三维可视化。后端具有图谱、节点、关系的查询及维护接口。图谱用于理解信息之间的关联；一条节点关系被可视化，不意味着它已经通过正式法源或个案适用性审查。

### 2.8 辅助工具、历史及其他功能

辅助工具包括法律计算器、法律日历、诉讼时效查询，以及诉讼费、工伤赔偿、律师费、违约金、保全费、执行费、遗嘱费、公告费、鉴定费、仲裁费等估算页面。各工具根据不同参数给出参考结果，适用地区、日期、收费标准和特殊情形仍需核对。平台还有历史记录、收藏、智能体管理和设置等页面；不同业务记录保存在各自的模型和接口中，不能把“历史记录”理解为全站共用一张数据表。

### 2.9 这些模块的关系

平台支持按需求**独立使用或组合使用**。例如房屋租赁押金纠纷，用户可以先问法小助，再用案情推断理清双方说法，用纠纷整理列出证据缺口，查找相似文书，最后起草沟通函；有合同文件时可另外做合同审查。这是用户选择的使用路径，不代表系统会自动把所有模块输入互相同步。另一个例子是劳动争议：咨询后由用户进入案件工作台，才会走下面所述的正式材料、事实、分析和草稿流程。项目中的[虚构案例资料](./项目讲解与案例演示.md)分别覆盖了租赁、合同和劳动场景。

## 3. 平台中的咨询与劳动案件办理

**法小助咨询**解决“我遇到了什么问题、接下来去哪里”。用户可以用自然语言提问，查看多轮回答和历史会话；数字人用表情、动作和语音状态呈现交互。回答中的功能建议使用真实页面路由，用户点击后才进入相应功能。普通聊天不会因为一句法律问题就无条件执行任意法律 Agent。

**案件工作台**解决“围绕一件具体纠纷，怎样有步骤地处理”。它是顶栏“案件与纠纷”中的独立入口，而不是把完整办案表单塞进聊天框。聊天里可出现“转入办理/继续办理”的上下文动作，但正式的材料、事实、法源、运行步骤、审批和导出都在工作台。两种视图共享相关会话与案件上下文，用户切换时可以继续原来的交流或办理。

法小助对劳动问题有受控分流能力：系统结合当前输入和已知事实判断是否属于劳动咨询、劳动关系初筛、正式劳动纠纷、非劳动纠纷或高风险情形。事实不足时继续追问，高风险时停止自动推进。模型可以参与理解和提出建议，但建案、启动任务等有副作用的动作必须通过服务端确定性条件授权；模型不能自行获得这些权限。

## 4. 重点模块：一件劳动争议的完整过程

下面以一件虚构加班费争议说明用户和系统各做什么。仓库中的[虚构案例材料](./项目讲解与案例演示.md)可供实际体验，但以下流程本身不依赖某个特定数字。

### 4.1 提出问题与建立案件

用户可先向法小助叙述“公司安排加班，部分加班费未支付”。对话用于澄清诉求和引导入口；聊天记录不是已确认的案件事实。进入案件工作台后，用户填写办理目标，创建或选择一个 Matter（案件工作区），并明确确认中国法域。法域未确认时，法律工具不能按默认猜测继续执行。案件会关联后续材料、事实、分析运行和草稿。

### 4.2 整理材料

用户可以粘贴文字，也可以按页面支持的类型上传文件。工作台接收材料后给出整理稿、材料列表、可能缺少的材料和事实线索。对于劳动场景，项目有面向实习协议、劳动合同、Offer、解除通知、考勤、工资记录、聊天记录等材料的适配器。系统提取的是**候选事实**：每项保留所来自的材料、原文片段及位置，便于回看。

候选不会仅因被识别就成为正式事实。用户应检查文字识别、日期、金额、主体和上下文，再选择采用、修改或不采用；材料没有给出的内容不能靠系统补造。例如当地上年度职工月平均工资未出现在材料中，就应保持缺失并提示补充。

### 4.3 确认事实与证据

在“事实与证据”阶段，用户检查候选、时间线、已有证据和证据缺口，并填写正式劳动事实表单。系统根据争议类型动态要求不同信息。以加班费为例，工时制度与至少一类加班小时数是关键输入；涉及欠薪、解除、补偿或赔偿时，又需要对应的金额、时间、原因和请求等事实。

页面显示当前尚缺项目，并在必填事实未齐时拦截正式分析。红色星号表达字段在当前规则下必填；“还缺 N 项”表达目前有多少项尚未满足。即使字段已填，必填属性仍保持。这种设计让用户能区分“这个字段必须有”和“当前尚未填写”。

证据层并非只罗列文件。它将已确认事实、材料支持、冲突及缺口关联起来，方便判断哪些主张有材料支撑、哪些仍需补证。但系统不会据此自动作出具有法律效力的证据认定。

### 4.4 分析、法源与风险

用户补齐必要事实后发起分析。系统可处理劳动关系、欠薪、试用期、解除、经济补偿或违法解除赔偿、加班费等问题，也支持一个案件包含多个争议标签。对于复合案件，运行计划按已注册模板组合所需步骤，公共的证据、期限、法源和审批步骤避免重复。

结果包括初步结论、争议焦点、金额估算、事实与证据引用、假设、警告、风险和待确认项。计算结果是基于当前输入和规则口径的参考值，不等于仲裁支持金额。期限判断需要起算事实，且中止、中断等情形仍须人工复核。

法律依据不是由模型临场编一段“看起来正确”的法条。项目保存官方来源、版本、适用法域、生效状态、获取时间和内容校验信息。执行时会验证相应引用的有效性；所需事实或可信法源不足，就暂停或阻断相关结论。分析页还会按本案争议类型展示相关的已验证官方来源。页面的法源目录展示与实体规则的引用门槛分开，不能因为页面显示某条来源就绕过规则校验。

### 4.5 人工确认与草稿

分析满足相应条件后，运行状态会等待用户明确确认生成仲裁申请草稿。未确认时不生成；确认后才保存草稿并允许预览、导出 Word 或 PDF。生成前会汇总期限分析和实体规则实际使用的法律来源，并再次核对引用有效性；若来源失效则停止生成。草稿和导出文件均保留“待人工复核”的定位，也没有自动提交仲裁的功能。

整条链路可以概括为：**用户叙述 → 材料候选 → 用户确认的事实 → 受控分析 → 用户审批 → 待复核草稿**。每个箭头都是一个需要检查的边界，不能把前一环节的内容直接当作后一环节的结论。

## 5. 系统架构

```text
用户浏览器
  └─ 经 Nginx 访问
       ├─ Next.js 前端：各业务页面、法小助、案件工作台、交互状态
       └─ Flask API：普通 HTTP、SSE 流式接口、庭审 WebSocket
            ├─ 通用法律业务：咨询、合同、案例/分析、纠纷、文书、图谱、计算工具
            ├─ 数字人会话：消息、记忆、分流、语音、会话与工作台上下文
            └─ 法律 Agent：案件、劳动领域、计划、工具、验证、审批、草稿

Flask 各业务模块按需要使用的依赖：
  ├─ SQLAlchemy → PostgreSQL（业务数据、运行状态、法源与审计）
  ├─ 材料/上传文件存储
  ├─ 外部 AI 模型接口（由需要模型的后端服务调用）
  └─ 官方法律来源（法源服务同步、复核后存储；劳动办案读取已验证法源）
```

这是**整个仓库的主要运行结构**，不是说所有业务都会经过法律 Agent。合同审查、文书起草、知识图谱和计算工具各有自己的 Flask 路由与服务；劳动案件 Agent 只是后端业务层中的一条较完整的受控流程。浏览器访问前端页面，也通过 `/api` 与后端交互；SSE 用于流式返回，WebSocket 用于模拟庭审的双向通信。Nginx 在提供的 Docker Compose 部署方案中把 `/` 转发给 Next.js，把 `/api/` 转发给 Flask。本地开发可能使用 Next.js 的 API rewrite，不能把某一种代理方式当成全部环境的固定路径。

外部 AI 模型由后端服务调用；PostgreSQL 负责保存数据，不调用模型。官方法律来源由后端法源 Provider/同步与复核流程获取、治理并存入数据库；具体法律分析从已存储的法源中取引用并校验。法源同步与普通用户浏览页面属于不同流程。上传材料还涉及文件存储，因此持久化也不只有数据库。

### 5.1 前端

前端采用 **Next.js 14、React、TypeScript、Tailwind CSS 和 Zustand**。首页、各法律功能页、法小助和工作台均位于同一个前端项目。`digitalHumanStore` 管理会话和工作台相关的共享前端状态；工作台的跨阶段动作集中在 `useMatterWorkspace`，四个阶段组件负责展示与交互，避免每个页面各自复制一套业务流程。

数字人视觉使用本地 **Rive** 资源和状态机。聊天、悬浮入口及工作台助手复用业务状态映射；它主要表达聆听、思考、回答等交互状态，不承担案件审批。普通对话使用服务端流式事件，语音能力包含浏览器语音输入和回复朗读；相关功能受浏览器权限、服务和环境支持影响。

### 5.2 后端与业务服务

后端是 **Flask**，不是 FastAPI。`flask_app/app.py` 注册法律咨询、合同、分析、纠纷、文书、知识图谱、法律工具、收藏、智能体管理、数字人会话和数字人 Agent 等 Blueprint。各路由把请求交给对应的业务服务：例如合同上传与审查、案例分析、纠纷处理、图谱节点与关系、文书生成、计算工具，以及数字人对话和劳动案件处理。数据库访问由 SQLAlchemy 管理，结构迁移由 Alembic 管理。合同审查等使用 SSE 逐步返回内容，模拟庭审使用 WebSocket。

项目通过 OpenAI-compatible 接口调用外部模型。模型适合处理自然语言问答和辅助理解，但法律任务的工具清单、计划模板、法域校验、预算、审批和结论验证由后端程序约束。外部模型可用性取决于实际部署配置；仓库不包含可代替模型服务的保证。

### 5.3 法律 Agent 的执行方式

法律 Agent 位于上述后端业务层，主要承接当前的劳动案件深度流程，不能代表整个后端。劳动案件使用一套通用的 `CapabilityRuntimeGraph`，劳动领域能力以领域包和模板接入，不为欠薪、加班或解除各复制一套执行图。一次运行称为 Run；系统先检查案件上下文，再从已注册模板生成本次的 Plan revision，随后逐个处理步骤：选择工具、执行、观察结果、验证、决定下一步。每个工具来自白名单，执行前检查参数、法域、审批和预算。

验证失败时，系统可能重试、要求补充事实、因法源不足阻断、等待人工审批或移交人工；不会把所有失败都包装为“分析完成”。Plan revision、步骤、工具调用、审批和结果快照会保存，便于恢复任务与追溯过程。模型不能自由创建工具，也不能替用户点击审批。

## 6. 关键数据与状态

整个项目并非只存劳动案件数据。普通咨询保存会话和消息；合同审查保存合同与风险结果；案情、纠纷、文书、知识图谱、日历及计算工具也有各自的业务记录。它们在同一个后端和数据库环境中工作，但接口、数据模型与业务流程各有分工。下表中的 Session、Matter 和 Run 专指数字人及劳动案件深度流程，不应拿来解释所有页面的数据结构。

| 概念 | 含义与用途 |
| --- | --- |
| Session（会话） | 保存法小助的多轮消息及恢复上下文；同一会话可以与案件关联。 |
| Matter（案件） | 一件具体法律事务的数据归属边界，承载目标、法域、材料和确认事实。 |
| Workspace State | 保存当前会话选中的案件指针及版本；刷新、切换会话后按服务端状态恢复，避免单靠浏览器缓存猜测当前案件。 |
| Triage（分流） | 保存劳动问题的场景、争议标签、缺失事实、风险等级、推荐处理类型及版本。 |
| Run / Plan / Step | 分别表示一次受控任务、该任务采用的版本化计划和计划中的单个执行步骤。 |
| ToolCall / Verification | 记录工具输入输出、验证结果和错误，供结果展示、恢复及审计使用。 |
| Authority（法源） | 保存法律来源的发布主体、版本、状态、适用范围、正文与校验信息；具体引用须重新验证。 |
| Artifact（成果） | 保存经审批生成的草稿及其事实、材料和法源引用。 |

当前数字人链路使用浏览器匿名客户端标识校验会话、案件和运行归属，并非完整的账号登录和跨设备权限体系。因此项目资料不应将它描述为已经建成统一的用户账号权限平台。关键写操作和聊天请求有幂等与恢复机制；重复提交同一请求不应凭空生成多个案件或重复副作用。不同层的取消语义也有区别：聊天请求可停止后续流式处理，Agent Run 的取消会记录任务状态，不等同于强制中断任意底层线程。

## 8. 项目设计重点

1. **多种任务共用一个平台入口**：用户可从咨询进入合同、检索、纠纷、文书、模拟法庭、图谱或工具，也可以直接使用目标功能；不必为每个问题另找一套系统。
2. **功能分工明确**：咨询负责解释与引导，合同审查针对合同文本，纠纷整理梳理叙述，文书起草生成草案，辅助工具进行参数测算；劳动案件工作台承担更严格的持续办理。
3. **重点案件强调事实出处**：劳动材料候选记录原文位置，用户决定是否采用；已确认事实与只在聊天中提过的信息不混同。
4. **受控执行与可追溯结果**：劳动 Agent 依据模板调用白名单工具，验证事实、规则和法源，保存运行计划、步骤与审批；信息不足时允许暂停或阻断。
5. **人保留最终决定权**：全站的 AI 内容和参考测算都需核对；劳动仲裁草稿尤其需要明确审批和专业复核，平台不执行正式提交。

## 9. 当前完成情况与使用边界

从当前源码看，首页与顶栏组织的普法问答、合同审查、法律检索、案件与纠纷、文件起草、模拟法庭、法律图谱、辅助工具及历史记录均有对应页面和后端能力。劳动案件工作台还接入分流、材料候选、动态事实表单、规则分析、法源验证、草稿审批与导出。项目记录中有前端类型检查、后端专项回归和部分浏览器验证；它们分别证明对应代码或检查范围，不能替代对每个部署环境、每个法律场景和所有设备的现场验证。

尤其需要区分：

- **法律结论**：系统输出是初步分析，事实、证据效力、法律适用和金额需要人工复核；不能宣传为自动法律代理或保证结果。
- **法律来源**：开发测试环境中经过审核的法源状态，不自动等于其他部署环境中同样可用；实际分析会受该环境法源同步和验证状态影响。
- **模块成熟度**：合同、模拟法庭、知识图谱、计算器等是真实项目功能，但各模块的实现深度不同，不能把劳动案件链路的验证结果推广成全站能力的统一保证。
- **真实运行**：本说明核对的是项目文件与既有记录，未在本次文档整理中启动完整生产部署或执行现场法律专业验收。

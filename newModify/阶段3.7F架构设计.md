# 阶段 3.7F（第一部分）架构设计：SSE增量呈现

## 1. 结论

3.7F第一部分不改动聊天编排、工作台或 Agent 业务，而是在 3.7D 唯一会话主链上增加一层"已验证回复的增量呈现"：

```text
POST /api/digital-human/chat        （保留，兼容旧客户端）
POST /api/digital-human/chat/stream （新增，SSE增量呈现）

Orchestrator 完整处理（解析→路由→安全校验→持久化）
  → 已验证 reply 按字符分块
  → SSE: accepted → thinking → delta* → completed
```

本阶段是"SSE增量呈现"，不是原始 LLM Token 流式输出：前端先看到加速出现的完整回复，业务状态（session、emotion、decision、action、workspace）仍以 completed 事件为准。

## 2. 事件契约

所有事件携带 `request_id`：

| 事件 | 载荷 | 含义 |
| --- | --- | --- |
| `status: accepted` | status, message | 请求已受理 |
| `status: thinking` | status, message | 正在处理（LLM与业务动作期间） |
| `delta` | text | 已验证回答的文本增量 |
| `completed` | 完整聊天响应 | 与 `POST /chat` 的 result 一致，用于 session、emotion、decision、action 和 workspace 同步 |
| `error` | error、code、retryable | 稳定中文错误、错误码、是否可重试 |

约束：

- completed 中的完整 reply 必须等于全部 delta 按序拼接。
- 错误码稳定：`REQUEST_IN_PROGRESS`（可重试）、`FORBIDDEN`、`NOT_FOUND`、`INVALID_INPUT`（不可重试）、`DATABASE_UNAVAILABLE`、`INTERNAL_ERROR`（可重试）。
- 入参校验失败发生在流开始前，仍返回 JSON 400，与 `/chat` 一致。
- 通用异常不把原始异常文本透传给前端。

## 3. 服务端设计

### 3.1 SSE 工具模块

`services/conversation/sse.py`：

- `encode_event(event, data, request_id)`：单条事件编码，request_id 必带且不可被载荷覆盖。
- `iter_text_chunks(text, size=12)`：按字符分块（CJK 安全），拼接与原文一致。
- `stream_error_data(exc)`：异常 → 稳定错误载荷。
- 常量：`DEFAULT_CHUNK_DELAY = 0.02s`（相邻 delta 的呈现间隔，测试可置 0）。

### 3.2 chat_stream 生成器

`DigitalHumanService.chat_stream()` 与 `chat()` 共享同一输入校验、LLM 配置与 Orchestrator：

```text
校验（问题、session_id、request_id）
→ yield accepted
→ yield thinking
→ orchestrator.chat(...)   # 完整解析、路由、安全校验、持久化
   ├─ 异常 → yield error（稳定映射）→ 结束
   └─ 成功 → yield delta*（按字符分块 + 呈现间隔）
→ yield completed（完整 result）
```

- 生成器先完整复用 `chat()` 的幂等与恢复：同一 request_id 重试时 Orchestrator 直接返回已持久化缓存，不重复创建 Matter 或 Run。
- 服务端没有取消能力：客户端断开后生成器在下一个 yield 处停止，但 Orchestrator 的持久化已先完成，消息仍可通过历史恢复。

### 3.3 路由

`POST /api/digital-human/chat/stream`：

- 与 `/chat` 相同的请求体与参数校验；客户端身份仍走统一身份解析。
- 响应 `Content-Type: text/event-stream; charset=utf-8`；
  `Cache-Control: no-cache, no-transform`；
  `X-Accel-Buffering: no`（关闭 Nginx 等代理缓冲）。
- 校验失败返回 JSON 400/403/503，与 `/chat` 相同映射。

## 4. 前端设计

### 4.1 API 层

`digitalHumanApi.ts` 新增 `sendDigitalHumanMessageStream()`：

- 使用现有 `request()`（统一请求头、凭据与超时），fetch 返回后通过 `response.body.getReader()` + `TextDecoder` 解析 SSE 块（不用 EventSource）。
- `onStatus` / `onDelta` / `onStreamFallback` 回调；`completed` 事件解析为 Promise 结果；`error` 事件抛出 `DigitalHumanStreamError`（含 code、retryable）。
- 浏览器不支持流式读取时降级调用 `sendDigitalHumanMessage()` 并触发 `onStreamFallback`，显示明确中文提示，不静默吞错。
- AbortError、解析失败、流中断分别转换为明确中文错误。

### 4.2 Store

- 新增 `streamingMessage`：唯一一条正在增量显示的临时 assistant 消息；completed 后才替换为最终消息并同步 session、emotion、decision、action 与 Workspace。
- 增量期间 `isLoading` 保持，组件不渲染打字点动画，只渲染增量气泡。
- `cancelRequest`、`loadSession`、`deleteSession`、`startNewConversation`、`selectCurrentMatter` 均清理 `streamingMessage`；操作序列（`conversationOperationSequence`）继续防止迟到响应覆盖。
- 临时消息不进持久化（partialize 仍只有 sessionId），刷新后从历史恢复完整消息。

### 4.3 组件

- `DigitalHumanChat`：消息区渲染 `streamingMessage`（尾部光标动画）；流式降级提示。
- `DigitalHumanCompanion`：`recentMessages` 包含 `streamingMessage`，侧边与主对话连续显示。
- 两种模式继续共用 `ConversationComposer` → 同一个 `sendMessage`。

## 5. 范围边界

本阶段不实现：

- 服务端取消：AbortController 只停止前端读取；不得伪装成已中止模型执行。
- 原始 LLM Token 流式输出：delta 来自解析、路由、安全校验和持久化之后的已验证回复。
- 语音、口型、AvatarController 与新动画状态机。
- 数据库结构或迁移变更；劳动 Agent、仲裁流程、法源与审批边界变更。

## 7. 验收矩阵

- 事件顺序固定为 accepted → thinking → delta* → completed；所有事件携带 request_id。
- 全部 delta 拼接等于 completed 的 reply；completed 与 `/chat` 的响应结构一致。
- 同一 request_id 重试复用缓存：Matter 与 Run 数量不增加。
- 流中断后：服务端已完成消息可通过历史恢复；前端不残留半条正式 assistant 消息。
- 错误事件包含稳定中文错误、错误码与是否可重试；通用异常不泄露原始异常文本。
- 校验失败返回 JSON 400/403，与 `/chat` 相同。
- 响应头：no-cache 且 `X-Accel-Buffering: no`。
- 完整聊天与工作台侧边陪伴共用同一 `sendMessage`，增量消息两端连续显示。
- 3.7D 单入口、请求幂等、法源/高风险失败关闭及 3.7E 工作台恢复全部回归。

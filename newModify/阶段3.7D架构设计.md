# 阶段 3.7D Conversation Foundation 架构设计

实施状态：`READY_FOR_ACCEPTANCE`（2026-07-27）。架构已按本文落地，自动化验证通过，等待用户会话体验确认。

## 1. 结论

3.7D只建立统一会话基础，不重写Agent Runtime，也不提前实现流式、实时取消、语音或工作台侧边数字人。

当前双入口：

```text
前端 sendMessage → DigitalHumanService → 普通回复
                └→ isLaborQuestion → useLaborTriage → Matter/Triage/Run
```

目标单入口：

```text
POST /digital-human/chat
  → ConversationOrchestrator
    → Memory / ContextBuilder
    → ConversationRouter
    → 受控 Action
    → 普通回复 或 既有 Matter/Triage/Agent Facade
```

## 2. 边界

- Conversation负责“理解当前会话并选择下一步”；`CapabilityRuntimeGraph`继续负责案件执行。
- Router只输出决策，不创建Matter、不启动Agent、不审批。
- Orchestrator只调用已有Matter、劳动分流和Agent Facade，不直接访问Runtime节点或领域工具。
- Conversation Memory不是证据库。只有用户消息可以形成 `user_claim`/`candidate_fact`，且必须保存来源消息ID；Assistant内容不得成为正式事实。
- Matter已确认事实优先于聊天记忆。冲突时提示用户去工作台确认，不静默覆盖。

## 3. 模块设计

新增 `flask_app/services/conversation/`：

| 模块 | 单一职责 |
| --- | --- |
| `schemas.py` | RouterDecision、ConversationAction、MemorySnapshot、ContextEnvelope等封闭契约 |
| `token_budget.py` | 保守Token估算、分区预算和Recent Window选择 |
| `repository.py` | 原始消息、Memory快照和请求幂等的数据访问 |
| `memory.py` | 从用户消息更新结构化记忆、撤销/替换旧陈述、生成滚动摘要 |
| `context_builder.py` | 按固定优先级组装模型上下文并处理冲突 |
| `router.py` | 高优先级确定性规则 + 模糊场景结构化LLM决策 |
| `actions.py` | 对现有Matter/Triage/Agent Facade的窄适配 |
| `orchestrator.py` | 编排一次请求，保证单入口、幂等、失败关闭 |

`DigitalHumanService`保留现有公开方法，内部委托Orchestrator，避免继续扩成超大文件。

## 4. 数据设计

保留 `digital_human_messages` 作为完整Raw Messages。新增：

1. `conversation_memories`
   - `session_id`：一会话一行，外键级联删除。
   - `schema_version`、`revision`：版本化与并发保护。
   - `structured_json`：主题、用户目标、会话阶段、Matter关联、带来源的用户陈述、已确认决定、待解决问题。
   - `summary_text`：供模型和用户阅读的自然语言摘要，不作为事实冲突判断或正式案件事实来源。
   - `summary_items`：可治理的摘要条目，至少保存 `item_id`、`item_type`、`subject`、`value`、`source_message_ids`、`status`、`supersedes_item_id` 和 `updated_at`；重要事实、用户目标、决定和待解决问题必须结构化。
   - `summary_through_message_id`：标记摘要已覆盖的消息边界，只压缩Recent Window之外的旧消息。
   - `created_at`、`updated_at`。
2. `digital_human_messages`新增可空 `request_id` 与 `estimated_tokens`。
   - `(session_id, request_id, role)` 唯一，避免重试产生重复消息。
   - 历史数据的Token在读取时惰性估算，不做高风险全表重写。

所有结构变更通过新Alembic revision完成，不依赖 `create_all` 演进生产库。

## 5. Memory与Context规则

上下文固定优先级：

```text
安全规则/当前输入
> Matter已确认事实
> Agent真实状态
> 最新用户陈述
> Structured Memory
> Rolling Summary
> 较旧聊天
```

预算分区必须保护安全规则、当前输入、Matter事实和Agent状态；预算不足时先移除旧聊天，再压缩摘要。Structured Memory中的用户陈述保存 `source_message_id`、状态和替代关系；“不是A，是B”等修正会把旧项标记为 `superseded`，不会改写历史消息。

Rolling Summary只汇总已落库且位于Recent Window之前的内容；摘要不得生成新事实。其契约为：

```text
Rolling Summary
= summary_text（可读投影）
+ summary_items（冲突治理与来源追踪）
```

- `summary_text` 必须由当前有效 `summary_items` 和非事实性会话概述重新生成，不能作为需要字符串切片修改的事实容器。
- ContextBuilder只依据 `summary_items` 做冲突判断；与Matter正式事实冲突的条目不进入上下文，并记录确定性排除原因。
- 用户说“不是6500，是7200”时，旧工资条目标记为 `superseded`，新条目引用当前用户消息并通过 `supersedes_item_id` 指向旧条目；随后重建 `summary_text`。
- 无法可靠结构化或缺少来源消息的摘要事实不得进入有效 `summary_items`，最多保留为不参与事实推理的会话概述。

## 6. Router与Orchestrator契约

Router输出仅允许：

```text
normal_chat | labor_consultation | labor_triage | matter_interaction
agent_continue | workspace_guidance | high_risk_handoff
```

Orchestrator动作仅允许：

```text
reply_only | ask_one_key_question | create_matter | guide_to_workspace
start_agent | continue_agent | request_approval | stop_for_risk
```

执行约束：

- 每轮最多追问一个关键问题。
- 劳动关键词本身不能触发 `create_matter`。
- 高风险规则优先于LLM Router。
- 法源阻断、审批、人工接管和预算错误直接投影真实状态，Conversation不能改写为成功。
- 同一 `request_id` 只允许一次有效动作；重试返回已完成响应。

兼容响应继续保留 `reply`、`intent`、`emotion`、`route`、`route_label` 和 `session_id`，新增版本化 `decision`、`action` 与轻量上下文引用，前端可渐进迁移。

## 7. 实施增量

1. 契约与存储：迁移、Repository、Raw Messages幂等和Token Budget。
2. Memory与Context：Structured Memory、冲突规则、ContextBuilder。
3. 长对话：Rolling Summary及30～50轮稳定预算测试。
4. 单一Router：确定性高风险/状态规则与结构化LLM回退。
5. Orchestrator与入口收口：后端受控动作；前端删除 `isLaborQuestion → laborTriage.start` 提交副作用，保留工作台事实补录能力。

每个增量独立回归，前四步稳定后才切换前端入口。

## 8. 验收与回归

- 30～50轮后用户目标仍正确，模型输入Token在摘要后趋于稳定。
- 用户修正旧陈述后旧候选不再进入有效上下文。
- Rolling Summary中的重要事实均可按类型和来源定位；修正旧事实时通过条目失效与重建文本完成，不对自然语言摘要做脆弱切片。
- Assistant推测进入Matter正式事实数量为0。
- 同一输入只产生一个RouterDecision和一个主动作。
- 普通咨询不创建Matter；明确案件处理且满足最低分流条件时才创建。
- 清除/重试请求不产生重复消息、Matter或Run。
- 高风险、法源不足、审批和人工接管继续失败关闭。
- 阶段0会话/幂等测试、3.7A分流、3.7B组合Plan、3.7C规则与前端类型检查全部回归通过。

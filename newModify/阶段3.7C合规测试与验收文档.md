## 2. 测试目的

确认劳动纠纷 Agent 能在同一案件和同一 Runtime 中完成：案件创建、法域确认、材料解析、事实确认、动态计划、欠薪/试用期/解除/补偿赔偿/加班费规则计算、法源校验、人工审批和仲裁草稿生成。

本轮特别验证：

1. 页面不得向用户显示 `wage_arrears_amount_or_salary_and_months` 等内部字段名。
2. “加班费”必须进入稳定争议标签、事实表单、规则步骤、法源校验和结果展示。
3. 关键事实或有效法源不足时必须暂停，不得生成确定性法律结论。
4. 仲裁草稿必须经用户明确批准后生成。

## 3. 合规边界

### 3.1 测试数据

- 只使用虚构姓名、虚构单位和虚构案件材料。
- 禁止上传真实身份证号、银行卡号、联系方式、住址、健康信息或未脱敏劳动材料。
- 测试截图和缺陷记录不得包含真实个人信息。
- 测试结束后，按环境管理要求删除临时上传文件和无保留价值的测试案件。

### 3.2 法律结论

- 所有规则结果均为初步核对或受控估算，`manual_review_required` 必须为 `true`，`legal_conclusion` 必须为 `false`。
- 综合计算工时制、不定时工作制或工时制度不明时，不得套用标准工时公式。
- 加班事实、单位安排、工资基数、调休和付款情况必须结合考勤、排班、聊天及工资记录复核。

### 3.3 法源审批

- 当前 4 个法源由用户明确授权以 `dev_test_approval` 在开发测试库批准，仅用于技术验收。
- 该批准不代表法律专业人员复核，不得复制到正式环境。
- 正式上线前必须清理测试法源数据、重新同步官网版本，并由有权限的法律专业人员逐条核对正文、效力、适用日期和条款后批准。
- 任一必需法源处于 `review_required`、`stale`、`sync_failed` 或缺失状态时，法源健康不得为 `ready`，依赖该法源的确定性分析必须失败关闭。

## 6. 用户完整调用链

```text
用户输入劳动问题
  → 创建 Matter
  → 用户确认中国法域和适用日期
  → 上传并解析材料
  → 用户采用或编辑材料候选事实
  → 系统标准化 dispute_tags
  → 唯一 CapabilityRuntimeGraph 生成组合计划
  → 核对证据缺口
  → 按标签执行五项可选实体规则
  → 统一计算仲裁时效并校验法源
  → 缺事实：awaiting_information → provide_information → 续跑
  → 缺法源：blocked_authority → 停止确定性结论
  → 规则与法源通过：awaiting_approval
  → 用户明确 approve
  → 生成劳动仲裁申请书草稿
  → 持久化结果、引用和审计记录
```

主要接口链：

| 阶段 | 方法与路径 |
| --- | --- |
| 创建案件 | `POST /api/digital-human/agent/matters` |
| 确认法域 | `POST /api/digital-human/agent/matters/{matter_id}/jurisdiction` |
| 上传材料 | `POST /api/digital-human/agent/matters/{matter_id}/materials` |
| 读取建议 | `GET /api/digital-human/agent/matters/{matter_id}/labor-dispute/suggestions` |
| 启动任务 | `POST /api/digital-human/agent/matters/{matter_id}/labor-dispute/run` |
| 补充事实/审批 | `POST /api/digital-human/agent/runs/{run_id}/continue` |
| 查看当前闭环 | `GET /api/digital-human/agent/matters/{matter_id}/labor-dispute` |
| 查看法源 | `GET /api/digital-human/agent/legal-authorities/labor` |

## 11. 缺陷分级与处置

| 级别 | 定义 | 发布要求 |
| --- | --- | --- |
| P0 | 数据泄漏、跨客户端越权、错误法律倍率、绕过法源/审批、无依据生成草稿 | 必须修复并全量回归，禁止发布 |
| P1 | 金额边界错误、关键字段不可填、引用丢失、错误产生法源版本 | 必须修复或由负责人书面接受风险 |
| P2 | 不影响业务结论的显示、文案或布局问题 | 可带已登记问题进入后续版本 |
| P3 | 优化建议 | 进入待办，不阻断验收 |

缺陷记录至少包含：编号、环境、案件ID、运行ID、复现步骤、实际结果、预期结果、截图/日志、严重级别、修复版本、回归结果和责任人。记录不得包含真实敏感信息。

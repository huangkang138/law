# 阶段 3.7F（第二部分）架构设计：服务端取消

## 1. 结论

3.7F 第一部分让用户"看到"增量回复；第二部分让用户"停止"它。停止不再只是前端 abort——服务端会真正中止在途模型执行：

```text
POST /api/digital-human/chat/cancel  （幂等）
  ├─ 进程级取消标志（同进程即时生效）
  └─ digital_human_requests.status = "cancelling"（跨 worker 持久信号）
在途 LLM 分块循环发现取消 → break + 显式 close()（中止 httpx 模型流）
  → 行落 "cancelled" 终态（保留检查点与资源）
  → SSE: accepted → thinking → error(code=CANCELLED, retryable=true)
同一 request_id 重试 → 按检查点幂等恢复 / LLM 阶段重跑
```

关键事实：对 `llm.stream()` 迭代器 break/close 会经 GeneratorExit → openai `Stream.close()` → httpx 响应关闭，真正中止底层 HTTP 模型请求（已查证 langchain_openai 1.3.5 / openai 2.45.0）。

## 2. 取消双通道

- **进程级标志**（`services/conversation/cancel.py`）：`request_id → threading.Event` 注册表（15min TTL 与请求租约对齐，惰性修剪）。`arm` 绝不重置已置位的标志；`set_cancelled` 在请求行尚未创建时也先生效。
- **DB 通道**：`status="cancelling"` 为持久取消信号；`is_cancelled(poll_db=True)` 按 0.5s 节流读库（只读 status，异常吞掉返回 False），命中则置位本地标志。覆盖多 worker 部署（停止延迟 ≤1s 量级）。

## 3. 状态机

```text
processing ──mark_cancelling(保留租约+检查点)──▶ cancelling ──在途线程 mark_cancelled──▶ cancelled（终态）
                                                            （_assert_lease → 清租约，保留 checkpoint/resources）
取消发生在各阶段的语义：
- LLM 阶段：chunk 循环 break + close → 无任何 Matter/Run 副作用
- 动作执行前：入口检查 → 完全不执行副作用
- 动作执行后/完成窗口：落 cancelled，检查点保留，重试幂等恢复（Matter/Run 复用）
- 动作执行中：不强制中断（劳动动作与 Runtime 安全边界）
- completed 后：no-op（取消端点返回 {cancelled:false, status:"completed"}）
重试语义（begin_request）：
- cancelled/cancelling(租约过期) + checkpoint → action_running（幂等恢复）
- cancelled/cancelling(租约过期) 无 checkpoint → processing（重跑）
- cancelling + 租约未过期 → raise ConversationCancelled（防穿透并发重跑）
```

## 4. 关键实现点

- `ConversationCancelled(Exception)` **不继承 RuntimeError**（避免被 /chat 的 `except RuntimeError → 409` 截获）；SSE 映射 `error(code=CANCELLED, retryable=true)`；非流式 /chat → 409 同码。
- `orchestrator.chat()`：`arm` 开头、`finally: disarm`；begin_request 前查进程标志（行未建时短路不落库）；begin_request 后带 DB 轮询再查；except 分支按 `ConversationCancelled` 分流到 `mark_cancelled`（而非 `mark_retryable`）。
- `_ensure_not_cancelled` 四个检查点：action_completed 快路径前、mark_action_started 前、普通 complete_request 前、动作执行前/后（执行中不检查）。
- `_stream_joined`：每 chunk 检查取消 → break；finally 显式 `close()`；循环后复查进程标志 → raise。重试的第二次 stream 同样检查。
- 会话级 advisory lock 仍是终局仲裁者：取消端点（mark_cancelling）与在途线程（mark_cancelled）都经锁串行化；双重 finalize 由 `_assert_lease` 决出先到者。
- 同会话活跃冲突查询把 `cancelling` 计入（`IN_FLIGHT_STATUSES`），防取消解除期间并发重跑。

## 5. 前端

- `cancelRequest`：先 fire-and-forget 调取消 API（携带在途 `activeRequestId`），再本地 abort + 清 UI。
- `sendMessage` 保存/清理在途 `activeRequestId`；收到 `error(code=CANCELLED)` 时不追加错误气泡，仅显示"已停止回复"轻量提示。
- SSE 事件契约不变（复用 error 事件），`DigitalHumanStreamError` 已携带 code/retryable。

## 6. 范围边界

不实现：服务端取消之外的能力（语音、口型、动画）；Runtime 执行中强制中断；数据库结构或迁移变更；对断连（非点击停止）的自动取消。跨 worker 取消延迟为轮询节流所致（0.5-1s），属已知边界。

## 7. 验收矩阵

- 长回复生成中按停止：增量立即停止、无后续回复、模型请求被真正中止（服务端日志/耗时佐证）。
- 取消后 DB 行 status=cancelled、租约清空；LLM 阶段取消无 Matter/Run 副作用；动作阶段取消副作用幂等保留且重试不重复创建。
- 同一 request_id 重试：LLM 阶段重跑成功、动作阶段按检查点恢复。
- 取消已完成请求：no-op；取消他人请求：403；行不存在：404。
- SSE 事件序列 accepted → thinking → error(CANCELLED)；前端无错误气泡、提示"已停止回复"。
- 取消后可立即正常发送下一条消息（会话不再阻塞）。

# 阶段 3.7E 架构设计：Conversation × Workspace

## 1. 结论

3.7E不重做聊天、工作台或Agent，而是在3.7D唯一会话主链上增加一层可恢复的 Workspace 投影：

```text
Session
  ├─ Conversation（3.7D唯一入口）
  └─ ConversationWorkspaceState（当前Matter指针）
         └─ Matter → Triage → 最新Agent Run
                         └─ ConversationPresenter（确定性只读投影）
```

前端只有两种呈现模式，不产生两套业务状态：

```text
完整聊天模式 ← 同一Store / 同一Session / 同一发送动作 → 工作台 + 侧边陪伴模式
```

## 2. 当前缺口

1. `loadSession()`只恢复消息，Matter/Run依赖持久化的 `laborContextBySession`。
2. 一个Session可关联多个Matter，现有外键只能表达“属于”，不能表达“当前选择”。
3. `useLaborTriage`按前端缓存中的 `runId` 恢复，缓存缺失即无法恢复。
4. 工作台展开后完整聊天列仍存在，没有“工作台主区域 + 侧边陪伴”的职责分离。
5. Agent状态文案散落在工作台组件，聊天侧没有统一Presenter。
6. `client_id`保存在localStorage；清空全部localStorage会改变访问身份，单靠服务端关系查询无法找回旧会话。

## 3. 服务端设计

### 3.1 匿名身份兼容

新增统一 `DigitalHumanIdentity` 解析器，替换两个Router中重复的 `_client_id()`：

- 首次仍兼容合法的 `X-Digital-Human-Client-ID`，并签发 HttpOnly、SameSite Cookie。
- 后续请求以有效Cookie为权威；请求头只作旧客户端兼容和首次引导。
- Cookie与请求头冲突时不得静默切换用户；返回稳定身份冲突错误或按兼容策略同步新本地缓存。
- 所有Session、Matter、Run读取继续校验同一 `client_id`，不得因为恢复功能放宽归属。
- 不在日志、响应或前端状态中暴露Cookie内容。

这不是完整账号系统；登录、跨设备恢复和权限体系仍属于阶段3.5。它只保证同一浏览器清空localStorage后身份不随之丢失。

### 3.2 Workspace当前指针

新增表 `conversation_workspace_states`：

| 字段 | 约束 | 含义 |
| --- | --- | --- |
| `session_id` | PK、FK Session、级联删除 | 一会话一行 |
| `active_matter_id` | 可空、FK Matter、SET NULL、索引 | 当前工作台案件 |
| `version` | 非空整数 | 乐观更新与并发测试 |
| `created_at` / `updated_at` | 时区时间 | 恢复与审计辅助 |

服务层在同一事务中校验：Session和Matter均属于当前客户端，且Matter的 `session_id` 等于目标Session。数据库外键负责实体存在，服务规则负责跨字段一致性。

指针更新时机：

- Conversation Actions创建Matter成功后设置。
- 工作台创建或选择Matter后设置。
- 删除当前Matter时清空；若该Session仍有Matter，按最近业务活动选择回退项。
- 旧Session没有状态行时，按 `Matter/Run/Triage` 最近活动时间确定一次并懒写入。

不保存 `active_run_id`。Run从当前Matter下按 `updated_at, created_at` 倒序读取，避免双指针漂移。

### 3.3 Workspace Context聚合

新增 `ConversationWorkspaceService`，通过一个接口恢复前端所需状态：

```text
GET /digital-human/sessions/{session_id}/workspace
```

响应主体：

```json
{
  "session_id": "dh_...",
  "matter": {"matter_id": "matter_...", "title": "...", "goal": "..."},
  "triage": null,
  "run": null,
  "presentation": {
    "version": "1.0",
    "state_key": "needs_information",
    "headline": "还需要补充案件信息",
    "summary": "请在工作台完成缺失信息后继续。",
    "requires_user_action": true,
    "next_action": {"type": "open_workspace", "label": "去工作台补充"}
  }
}
```

规则：

- 无Matter返回空工作台，不用404表示正常空状态。
- 有Matter但无Triage/Run时对应字段为 `null`。
- Run返回既有Facade快照，不复制Runtime状态模型。
- 聚合服务只读业务状态；选择Matter使用单独的幂等命令接口。
- 所有错误使用稳定错误码，数据库故障保持503，越权保持403。

### 3.4 Conversation Presenter

新增 `services/conversation/presenter.py`。它是无副作用纯函数，不访问LLM：

| Runtime状态 | Presenter状态 | 通俗动作 |
| --- | --- | --- |
| `planning/replanning` | `preparing` | 等待或查看工作台 |
| `executing/observing/verifying/deciding/retrying` | `processing` | 查看处理进度 |
| `awaiting_jurisdiction` | `needs_jurisdiction` | 去工作台确认法域 |
| `awaiting_information` | `needs_information` | 去工作台补充信息 |
| `blocked_authority` | `blocked_authority` | 查看法源阻断 |
| `awaiting_approval` | `needs_approval` | 去工作台审阅并确认 |
| `human_handoff` | `needs_human` | 查看人工处理提示 |
| `completed` | `completed` | 查看结果 |
| `failed/cancelled` | `stopped` | 查看原因或重新开始 |

未知状态必须映射为安全的“暂时无法确认进度”，不得把原始状态透传到聊天区。

Presenter只说明状态、下一步和是否需要用户动作；不解释法律结论，不替代工作台审批，不读取模型思维链。

## 4. 前端设计

### 4.1 Store恢复

`digitalHumanStore`新增：

- `workspaceContext`、`workspaceLoading`、`workspaceError`。
- `hydrateSession(sessionId)`：并行读取消息和Workspace Context，以一次状态提交完成切换。
- 请求序号或AbortController：防止快速切换历史会话时旧响应覆盖新会话。
- `selectWorkspaceMatter(sessionId, matterId)`：先提交服务端指针，再更新本地状态。

`laborContextBySession`降为运行期兼容缓存，并从 `partialize` 移除。localStorage只可改善启动速度，不能决定当前Matter/Run。

启动恢复：

1. 读取服务端会话列表。
2. 本地Session仍有效则使用；否则选择服务端最近更新的Session。
3. 调用 `hydrateSession()`。
4. 无历史会话则显示欢迎状态。

### 4.2 双模式组件

保持 `DigitalHumanChat` 为外壳，拆出小组件，避免继续膨胀：

- `ConversationThread`：同一消息列表。
- `ConversationComposer`：同一 `sendMessage()`。
- `ConversationPresenterCard`：只显示服务端投影。
- `DigitalHumanCompanion`：工作台侧边的头像、Presenter、精简消息和输入区。

完整聊天模式显示历史、完整消息和关键分流卡；陪伴模式以工作台为主，侧栏只保留当前Matter沟通、通俗进度和下一步。完整 `missing_facts`、材料、法源、步骤、审批按钮和导出继续由 `DigitalHumanMatterWorkspace` 负责。

## 5. 范围边界

本阶段不实现：

- SSE、流式文本、实时取消和AvatarController。
- STT/TTS、口型或新动画状态机。
- Trace、Guardrails平台和Evaluation框架。
- 新Domain、Runtime Graph、Plan、Tool、Verifier或审批协议。
- 聊天内完整表单、聊天直接审批或聊天自动写正式Matter事实。

## 7. 验收矩阵

- 清空localStorage但保留浏览器Cookie：恢复同一匿名客户端、最近Session和当前Matter/Triage/Run。
- 删除Zustand持久化缓存：恢复结果不变。
- 同一Session选择多个Matter：刷新后恢复最后一次服务端选择。
- 快速切换两个Session：迟到响应不能覆盖当前Session。
- Matter存在但Triage或Run不存在：返回可用空状态，不误报系统故障。
- 当前Matter删除：指针安全清空或确定性回退。
- 越权Session/Matter/Run：403且不返回任何摘要。
- Presenter全部Runtime状态有确定映射，未知状态安全降级，测试确认无LLM调用。
- 两种模式发送消息均走 `/digital-human/chat` 和同一Session。
- 聊天侧不显示模板ID、英文状态、原始JSON和完整步骤；审批仍只能在工作台完成。
- 3.7D Router/Orchestrator单入口、请求幂等、法源/高风险失败关闭及3.7C劳动闭环全部回归。

## 8. 待批准决策

推荐整体批准以下两点：

1. 使用 `ConversationWorkspaceState.active_matter_id` 明确表达当前案件，不用更新时间猜测长期状态。
2. 使用HttpOnly匿名身份Cookie满足“清空localStorage仍可恢复”，同时保留现有请求头兼容；不在3.7E扩展为完整账号系统。

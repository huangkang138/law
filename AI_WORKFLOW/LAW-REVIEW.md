# LAW-REVIEW｜阶段验收工作流

用于阶段完成后的独立代码验收。默认只读：发现问题只报告，不直接修改代码。

## 执行流程

```text
只读检查
→ 验证阶段目标
→ 检查关键调用链
→ 检查安全与一致性
→ 运行相关测试
→ 输出 P0 / P1 / P2 问题
```

Review 上下文优先限定为阶段需求、本阶段 Diff、相关测试和必要上下游实现。只有证据表明问题跨越公共 Runtime 时才扩大范围。

## 阶段与架构检查

重点验证：

```text
需求是否真正实现
→ 调用链是否真正接通
→ 状态是否一致
→ 安全边界是否保持
→ 测试是否能证明行为
```

检查：

- Router 是否出现业务编排。
- Facade 是否出现具体领域规则。
- 是否复制或绕过 `CapabilityRuntimeGraph`。
- 劳动逻辑是否错误进入通用 Runtime。
- 是否绕过 ToolRegistry、PolicyToolExecutor、Verifier 或审批。
- 是否破坏 Plan revision 或出现跨层直接访问。

## Runtime 检查

涉及 Runtime 时检查 `Run → Plan → Step → ToolCall → Verifier → Decision → Persistence`：

- RunStatus、StepStatus 与实际执行结果是否一致。
- 是否先提交状态、后发生响应失败。
- retry 是否产生重复副作用。
- 是否可能并发执行同一个 Run，锁粒度是否异常。
- Plan revision 是否被覆盖。
- Tool 结果是否进入 Verifier，Verifier 错误是否被忽略。
- completed 是否提前出现。
- awaiting_information、awaiting_approval 是否能够恢复。

## LLM 与法律安全边界

- LLM 不得直接授权副作用动作，输出必须经过服务端确定性校验。
- 用户输入不得被提升为高权限 system 指令。
- Prompt Injection 不得改变工具、任务、审批或归属。
- Tool 名称不得脱离白名单完全由 LLM 控制。
- Matter / Run 创建不得存在越权路径。
- 事实、法域或法源不足时必须暂停或失败关闭。
- `authority_refs` 必须经过有效性验证。
- 材料候选不得自动成为确认事实。
- 草稿、高风险结果和审批不得绕过人工复核。
- 不确定结果不得包装成确定法律结论。

## 测试验收

实际执行：

1. 阶段测试。
2. 修改模块测试。
3. 受影响核心公共模块回归测试。

测试通过不等于自动通过 Review。继续检查是否仅覆盖 happy path、只断言 HTTP 200、mock 掩盖真实调用链，或遗漏数据库最终状态、重复调用、权限审批、异常中断和并发事务。

## 问题等级

只报告有真实证据的问题：

- **P0**：严重安全或数据破坏、权限完全绕过、核心系统不可用。
- **P1**：生产阻断，包括错误副作用、状态不一致、重试重复、并发破坏，或审批、法源、验证边界可绕过。
- **P2**：需要修复但不阻断，包括真实边界遗漏、恢复能力不足、明显测试缺口或局部设计风险。

每个问题必须包含发生位置、真实调用链、触发条件和实际后果。不得用“可能有风险”“建议优化”等无证据表述凑数。

A
→ B

触发条件：
...

实际后果：

LAW-REVIEW 只负责发现、证明问题并给出修复方向。需要修复时另行进入 `LAW-DEV`，修复完成后再执行 `LAW-REVIEW`。

## 验收导读输出

用户要求“验收导读”“完整故事”“讲清最终效果”或“怎么人工验收”时，先完成本工作流的事实核验，再按 `MODES.md` 的 `ACCEPTANCE_GUIDE` 一次性输出。该输出可借用 LAW-DEV 的目标、调用链、Before → After、测试和人工检查结构，但仍然只读，不进入逐函数 LEARN，也不修改代码。

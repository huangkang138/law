# 执行模式

## FEATURE

明确功能的最小开发：核对用户目标与 CURRENT_TASK → 实现 → 验证 → REVIEW。任务文档更新不等于业务完成；Runtime、数据模型、跨模块架构、高风险法律边界或大重构优先 ARCHITECTURE。

## BUGFIX

复现 → 根因 → 最小修复 → 回归 → REVIEW。简单 Bug 不强制架构分析，禁止顺手重构。

## FRONTEND

明确页面/组件、视觉或交互目标、不可改区域、当前状态流和验收描述；最小范围修改 → `tsc --noEmit` → REVIEW → 用户视觉验收。保持业务逻辑不变。已有截图、目标页面、明确区域或视觉问题时直接分析并实施；只有视觉目标确实无法判断才提出一个有决策价值的问题。

## ARCHITECTURE

只分析：当前缺口、推荐设计、最小范围、核心模块、验收。新正式架构任务先初始化 CURRENT_TASK 为 PLANNED，再进入 DESIGNING；不自动修改代码。方案确认后进入 APPROVED，再按目标执行。

## REVIEW

默认只输出：是否完成、是否超范围、最高 3 个风险、是否建议接受。以真实用户目标、CURRENT_TASK、实际 diff、测试和验收为准。失败退回合适模式；仅 `FULL REVIEW` 输出完整审计。

## LEARN

禁止修改代码，保持 MAP → TRACE → STOP → CHECK。

- **MAP**：先给 5～7 节点局部地图，并区分“完整业务链”与“本次实际阅读顺序”。若为先理解核心而从中间开始，必须明确：完整业务链是 A → B → C → D；本次从 C 开始，A/B 按需要补看。
- **TRACE**：每次只讲一个函数/紧密逻辑块：当前位置 `A → B →【当前函数】→ C`、为什么存在、关键输入、关键输出、1～3 个核心逻辑、上游（谁调用/使用它）、下游（结果主要交给谁）、一句话记忆、下一站或真实导航方式。
- **STOP**：只说明主业务链，不展开全部调用者；无关初始化、框架、通用工具等默认停止。
- **CHECK**：讲完一站立即等待用户继续；完成主链后再做简短理解检查。

严格区分业务下一站和 IDE 导航：只有当前代码存在真实符号引用时才写“下一步 Ctrl+B → xxx()”。不是直接引用则写“下一站：xxx()”，并说明应使用全局/文件搜索或 `Alt+F7` 进入。禁止把业务链误写成 Ctrl+B 跳转链。
